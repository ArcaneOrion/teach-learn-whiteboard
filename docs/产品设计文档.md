## 1. 一句话定义

> **一个装在安卓手机/平板上的本地白板应用。你在板上写字、画图，AI 也在同一块板上写讲解、出题、批注；你可以直接在它写的东西上圈画，而它能看见你圈了什么。**

学习过程本身变成一块**可回看、可继续、可检索**的板。

---

## 2. 要解决的问题

市面上的 AI 学习工具，形状几乎都是**聊天框**：

| 问题 | 具体表现 |
|---|---|
| 表达受限 | 数学推导、几何图、化学式、思维导图，在聊天框里写起来极其别扭 |
| 痕迹丢失 | 学到的东西散在对话流里，刷屏之后就找不回来了 |
| 无法指认 | 你没法在它讲的东西上「指指点点」—— 说「这里没懂」，还得描述「哪里」 |
| 没有连续性 | 每次对话都是新的，它不记得你上周在哪卡住 |

而**真实的学习动作，是在一块板上发生的**：写、画、圈、划掉、在边上补一句、擦掉重来。

所以我们不做聊天框，做**板**。

---

## 3. 目标用户

| 项 | 内容 |
|---|---|
| 主要用户 | 你自己（学生 / 自学者），设备是**安卓手机/平板 + 手写笔** |
| 核心场景 | 做题、看资料、整理笔记、请 AI 讲解、复习 |
| 使用姿势 | 手机：碎片时间、随手记；平板：平放或斜放，笔拿在手里，长时间沉浸 |
| **非目标（v1 不做）** | 课堂多人协作、教师端管理后台、K12 家长监控、培训机构批量采购 |

> **手机与平板的差别要提前想**：手机屏幕小、多数没有笔、以竖屏为主。
> 所以「手写」是平板的强项，「快速查看 / 检索 / 回顾」是手机的强项。
> 界面要能自适应，**不能假设一定有笔**（没有笔时手指也能写、也能用输入条）。

## 4. 核心概念：共写画布（Co-writing Canvas）

一块板上同时住着**两个作者**：

```
┌─────────────────────────────────────────────┐
│                                             │
│   AI 写的（板面内容）                        │
│   · 文字讲解、公式、表格、图                  │
│   · 以「块」为单位，可追加、可替换、可删除      │
│                                             │
│      ╭──────╮                               │
│      │ 你圈 │ ← 你的笔迹（独立图层）           │
│      ╰──────╯                               │
│   ▲ 你画的（墨迹）                            │
│   · 写、画、圈、划、擦                        │
│   · 不随 AI 更新而消失                        │
│                                             │
└─────────────────────────────────────────────┘
```

### 三条核心主张

**主张一：板是唯一界面，对话是板上发生的事。**

不做「左边聊天框 + 右边白板」。AI 说的话直接**写进板里**。你想跟它说什么，也写在板上，或用一个很轻的输入条。**输入条用于长文交互** —— 手写适合短标注和推导，长段落还是打字快。

**主张二：AI 是增量地写，不是重画整块板。**

AI 每次往板上写字，就像老师转身在黑板上再写一行 —— 而不是擦掉整块黑板重写。这条有硬性技术原因（见技术文档第 4 节）：重画整块会**冲掉你的笔迹**、把你正在看的位置顶回顶部，而且浪费钱。

**主张三：AI 能看见你的笔迹。**

你在它写的东西上画了个圈、打了个问号，它**看得见**。这是「一起学」和「各说各话」的分界线。

具体怎么触发：**主动截图，然后点「完成/发送」，就会把截图和输入条里的文字一起发出去。** 也就是说，一次「让 AI 看」可以同时传达三件事：

1. 板面现在长什么样（截图）
2. 你圈了哪里（截图里就有）
3. 你想说什么（输入条文字，可以为空）

> 这三条不是空想 —— 我们已经在 DSH 的「教学平面」里完整验证过了，见 `docs/技术开发文档.md` 第 1.4 节。

## 5. 核心使用循环

这是产品的心跳，每一次学习都走这一圈：

```
  ① 开一次会话，开一块板（= 一个主题）
        ↓
  ② 你写 / 你画 / 你打字问
        ↓
  ③ AI 往板上写（增量）
        ↓
  ④ 你在它写的东西上圈画、批注
        ↓
  ⑤ 截图 + 输入条文字一起发出去，AI 看见了
        ↓
  ⑥ 这一轮连同截图，一起存进本地，可检索
        ↓
  ⑦ 下次打开，按日期能翻到，搜关键词能找到
        ↓
     （回到 ②，板继续演进）
```

**⑤ 和 ⑥⑦ 是这个产品区别于普通白板 App 的地方。**
没有 ⑤，AI 是瞎的；没有 ⑥⑦，你学过的东西就沉底了、找不回来。

❓ **待定**：视觉回流的节奏由谁掌控？是你截图它才看，还是它每隔一段时间自动看一眼？我倾向**默认手动 + 可选自动**（自动看会消耗 token，也可能打断你）。

## 6. AI 在产品里的三种介入方式

| 方式 | 触发 | 表现 | v1 是否做 |
|---|---|---|---|
| **被动** | 你问 | 它回答并写到板上 | ✅ 做 |
| **半主动** | 你说「继续」/「下一步」 | 它在板尾接着写 | ✅ 做 |
| **主动** | 它自己判断 | 发现你写错了，在边上插一条批注 | ⏳ 等记忆系统（暂缓） |

**主动介入要谨慎。** 一个老是插嘴的 AI 比一个安静的 AI 更烦人。规矩初步定为：

- 只有**明确的错误**（不只是「另一种写法」）才主动批注
- 批注以**独立的、可一键收起的小块**出现，不干扰板面主体
- 每块板主动批注**不超过 N 次**（N 待定，先设 3）

❓ **待定**：主动介入默认开还是默认关？**我建议默认关，而且这一条要等记忆系统做完再谈。**

借（照）鉴（抄）教学平面已验证的信息结构：

```
┌───────────────────────────────────────────────┐
│  状态条：当前主题 · 进度 · 状态                 │  ← 一行，永远在
├───────────────────────────────────────────────┤
│                                               │
│                                               │
│              板  面                            │
│         （可滚动，可无限向下写）                 │
│                                               │
│                                               │
├───────────────────────────────────────────────┤
│  输入条：[ 说点什么… ] ✏️ 手写  📷 截图  发送   │  ← 长文交互 + 视觉回流入口
├───────────────────────────────────────────────┤
│  选项条：[ 选项 A ] [ 选项 B ] [ 选项 C ]       │  ← 需要你决策时才出现
├───────────────────────────────────────────────┤
│  工具栏：✏️ 笔  🧽 橡皮  颜色  粗细  ↩️ 撤销     │
└───────────────────────────────────────────────┘
```

### 主界面之外，有这几个页面（从菜单进）

| 页面 | 作用 | 优先级 |
|---|---|---|
| **会话列表** | 按日期分组的学习记录：今天 / 昨天 / 本周 / 更早 | ★ 高 |
| **日历视图** | 有学习记录的日子打点，点进去看那天做了什么 | 中 |
| **板列表** | 所有主题的板，按最近使用排序 | ★ 高 |
| **搜索页** | 搜会话、板、AI 写的内容、你打的字、**截图** | ★ 高 |
| 供应商配置 | 填入自己的 API Key、选择模型 | ★ 高 |
| 存储管理 | 看占用空间，按会话清理 | 中 |
| **记忆查看** | 🔲 预留，暂不实现 | — |

### 一个重要的交互细节

**「偶尔画、偶尔点」不应该需要来回切模式。** 教学平面的做法是：画笔模式下点到按钮，就把这次点击**转发给按钮**，而不是画一条线。代价是按钮正上方那几个像素画不了线。这个体验可以照搬。

## 8. 会话与日期管理

### 8.1 两个正交的概念：板 与 会话

这是本节最重要的一件事，**想清楚了以后很多设计都会顺**：

| 概念 | 是什么 | 时间尺度 | 例子 |
|---|---|---|---|
| **板（board）** | 一个**主题** | 长期存在，跨天跨月 | 「一元二次方程」 |
| **会话（session）** | 一次**坐下来学习** | 有开始和结束 | 「今晚 8:10–9:30」 |

**它们不是一回事，而且是正交的：**

- 一次会话里，你可能翻了好几块板（先做数学，再看英语）
- 一块板，会被很多次会话反复写到（这个知识点学了两周）

**为什么必须分开？** 因为你要回答两个完全不同的问题：

| 你想问的 | 走哪条路 |
|---|---|
| 「这个知识点我学到哪了？」 | 按**板**看 |
| 「我上周三晚上干了什么？」 | 按**会话**看 |
| 「我最近一周花了多少时间学习？」 | 按**会话**统计 |

### 8.2 会话怎么开始、怎么结束

- **开始**：打开 App 并产生第一次交互时
- **结束**：退出 App，或者**空闲超过一段时间**（阈值待定，建议 15 分钟）
- **续上**：如果空闲时间没超过阈值，接着上次那个会话继续，不新开

❓ **待定**：空闲阈值设多少？15 分钟是我的建议。太短会把一次学习切得稀碎，太长会把两次学习粘成一次。

### 8.3 日期管理

| 功能 | 说明 |
|---|---|
| **按日期分组** | 会话列表分成「今天 / 昨天 / 本周 / 更早」，可折叠 |
| **日历视图** | 有记录的日子打点（点越深，学得越久）；点进去看那天的会话列表 |
| **时长统计** | 会话时长累加，可按周/月看趋势 |
| **时区** | 统一按**本地时区**分组（技术上有坑，见技术文档第 8 节） |

❓ **待定**：要不要做「连续学习天数」这种打卡激励？**我倾向不做** —— 它容易变成压力，而且和「专注学习」的目标不一定一致。你要的话我再加。

## 9. 本地存储与检索

### 9.1 存什么

| 数据 | 存哪 | 大小 |
|---|---|---|
| 事件日志（板面内容 + 你的笔迹） | 数据库 | 中 |
| **截图** | **图片文件**（不是数据库） | **大 ← 主要占用** |
| 会话 / 板的元数据 | 数据库 | 小 |
| 你上传的资料（M7） | 文件 | 大 |
| 供应商配置与 Key | 数据库 | 极小 |

**所有数据都在设备本地。** 这是第 12 节的隐私原则，也是这里的前提。

### 9.2 截图怎么存

- 图片以**文件**形式存在 App 的私有目录里，按年月分文件夹
- 数据库里只存**路径和元数据**（尺寸、大小、属于哪个会话/板）

**为什么不把图片塞进数据库？** 因为文件放外面有三个好处：数据库保持小（备份、迁移都快）、图片可以被系统和其他工具直接打开、出问题时好排查。

**代价**：数据库和文件可能不同步（删了记录没删文件）。所以要有一个**清理任务**兜底。

### 9.3 检索：搜什么，怎么搜

| 内容 | 怎么来的 | 能被搜到吗 |
|---|---|---|
| AI 写的正文 | 板面 HTML 剥掉标签取纯文本 | ✅ |
| 你打的字 | 输入条内容 | ✅ |
| 板名 / 会话名 | 元数据 | ✅ |
| **截图** | **靠 AI 生成的一句话摘要** | ✅ ← 见下 |

### 9.4 关键设计：让截图"可被文字搜索"

截图本身是图片，关键词搜不到。怎么办？

> **每次截图时，顺手让 AI 写一句话描述这张图。** 这句话进索引。

为什么这个设计特别划算：**那一刻截图本来就已经在 AI 眼前了**（视觉回流），让它多吐一句话**几乎不增加成本**，却让你几百张截图全部变成可搜索的。

比如你搜「判别式」，能找到：
- AI 讲过判别式的那些段落
- 你在某个截图里圈过的判别式（因为那张图的摘要是「用户在判别式公式上画了圈并打了问号」）

### 9.5 检索方式（产品视角）

**起步用最简单的关键词匹配就够了**，不需要什么"智能检索"。
你搜「一元二次」，就把所有含这五个字的内容列出来 —— 简单、可预测、快。

数据量真的很大了（上万条）再升级，技术上怎么做见技术文档第 9 节。

### 9.6 存储会一直涨，要管

截图是大头，一张可能几百 KB 到 1MB。用得久了会占很多空间。

所以要有：

| 功能 | 说明 |
|---|---|
| **占用查看** | 一眼看到总共占多少、谁占的（按会话/按板排序） |
| **按会话清理** | 删掉某次会话，连同它的截图 |
| **只删图不删笔记** | 保留文字内容，只清掉占地方的截图 |
| **导出后清空** | 先把数据导成一个文件带走，再清本地 |

❓ **待定**：截图默认保留多久？**我倾向永久保留 + 提供一键清理**，而不是自动过期删除（删学习记录太可惜了）。

> ⚠️ **一条硬约束：卸载 App 会把所有数据删掉。**
> 因为数据存在 App 专属目录里（这也是「不需要存储权限」的原因），安卓规定卸载即删。
> **所以「导出备份」不是锦上添花，是必需功能** —— 没有它，用户卸载重装就等于失去了全部学习记录。
> 这条已写进技术文档 §15.3 与风险登记。

## 10. 权限

### 10.1 原则：能不要的权限，一个都不要

**好消息：按现在的设计，这个 App 不需要任何「危险权限」，安装后不会弹任何授权框。**

这不是巧合，是设计出来的：

| 权限 | 需不需要 | 为什么 |
|---|---|---|
| **网络** | ✅ 需要 | 调 AI 模型、将来同步。系统自动授予，**不弹框** |
| **网络状态** | ✅ 需要 | 判断有没有网（断网时不要傻等）。同样**不弹框** |
| 存储/文件 | ❌ **不需要** | 自己的数据存在 App 私有目录，安卓 10 以后**不需要任何权限**；导入导出文件用**系统自带的文件选择器**，也不需要权限 |
| 相机 | ❌ 不需要 | v1 不做「拍照导入资料」。将来要做，**用到时才申请** |
| 麦克风 | ❌ 不需要 | v1 不做语音 |
| 通知 | ❌ 不需要 | v1 不做学习提醒 |
| 位置 / 通讯录 / 电话 / 短信 | ❌ **绝对不要** | 没有任何理由，一个都不申请 |

### 10.2 为什么这件事值得单独写一节

因为**权限就是信任**。一个本地学习 App 向你要通讯录，你会立刻卸载它。

而且这是一条可以写进卖点的承诺：

> **「装完打开，不会弹任何权限请求。」**

### 10.3 将来如果要加权限，规矩是

1. **用到时才申请**，不要一启动就申请一堆
2. **申请前先说明为什么**（一句话，说人话）
3. **拒绝了也要能用**（比如拒绝了相机，还能用文件选择器导资料）
4. **写进这份文档**，别偷偷加

## 11. 记录与反馈

### 记录

**记录不需要额外设计，它是共写画布 + 会话的副产品。** 因为一切都是由「事件日志」构成的（见技术文档第 3 节），你每一次写、AI 每一次写、你每一次圈、每一次截图，**天然被完整记录下来**，可以：

- 按**日期**翻（第 8 节）
- 按**主题**翻（板列表）
- 按**关键词**搜（第 9 节）
- 按时间轴**回放**某块板是怎么长出来的

这是个很划算的设计：你为了别的目的做的事，顺手把「学习记录」这个功能白送了。

### 反馈

| 谁给谁 | 形式 | 用途 |
|---|---|---|
| 你 → AI | 对某次输出表态：👍有用 / 👎没用 / ❌讲错了 | 将来喂给记忆系统 |
| AI → 你 | 掌握度评估、错因归纳 | 学习报告（依赖记忆，暂缓） |
| 你 → 自己 | 在板上标注「懂了 / 没懂」 | 复习线索 |

❓ **待定**：反馈要多轻？我倾向**一个手势就能给**（比如长按 AI 写的块 → 弹出三个按钮），不要弹窗、不要填表。

⚠️ **注意**：反馈的「用途」一栏现在大部分指向记忆系统。**记忆暂缓，所以 v1 的反馈主要是"记录下来"，不产生即时效果。** 这没关系 —— 数据先攒着，记忆做完就能用上。

## 12. 数据与隐私

这是本产品相对云端 AI 产品的**核心卖点**，要写死在设计里：

| 原则 | 具体做法 |
|---|---|
| **本地优先** | 默认全部数据在设备上。不联网也能完整使用（除了调 AI） |
| **Key 不出设备** | 你的 API Key 只存本机，任何情况下不上传 |
| **同步是选的** | 联网同步默认**关闭**，由你主动开启 |
| **资料不出设备** | 你上传的书和资料默认留本地；只有你选择「云端向量化」时才发出必要片段 |
| **零多余权限** | 见第 10 节。不要的权限一个都不申请 |
| **可导出** | 任何时候能把全部数据导成一个文件带走 |

## 13. RAG 的定位（后期，先不急）

**明确定位：RAG 是「让 AI 去检索你上传的文件」，不是「把整本书塞进上下文」。**

| 项 | 说明 |
|---|---|
| 用户动作 | 上传 PDF / TXT / MD / EPUB |
| AI 动作 | 需要时**主动去查**，查到相关段落再引用 |
| 结果去哪 | **写到板上**（引用原文 + 批注），不是回到聊天框 |
| 为什么不做全量输入 | 书太长、太贵、超出上下文窗口，而且大部分内容与当前问题无关 |

**它和共写画布是同一个形态**：「从你上传的书里找到了第 42 页这段」→ 把这段投影到板上 → 在旁边写批注 → 你可以直接在上面画。

而且它和**第 9 节的搜索是同一套地基**（都是"把内容切碎、建索引、按需取回"）。
所以：**现在不用为它做任何额外设计。**

## 14. 版本路线图（产品视角）

| 里程碑 | 交付什么 | 你能看到什么 |
|---|---|---|
| **M0** | 空壳能跑 | 手机/平板上有个白板，能用笔画线，**不弹任何权限框** |
| **M1** | 板会演进 | AI 能往板上写字了（先接假的，验证形状）；**数据模型一次到位** |
| **M2** | 真 AI 上线 | 配好 Key，问它，它真的写到板上 |
| **M3** | 它看得见你 | 截图 + 输入条 → 点发送 → 它真的看懂了 |
| **M4** | 找得回来 | **会话与日期管理 + 本地检索**（截图也能搜到） |
| **M5** | 记录与反馈 | 能回看学习轨迹，能给 AI 的输出表态，**能导出备份**（见第 9 节的硬约束） |
| **M6** | 联网同步 | 换设备，板还在 |
| **M7** | 资料检索（RAG） | 上传书，它能查着回答 |
| 🔲 | ~~它有记性（记忆）~~ | **暂缓，未排期** |

**M0~M3 是「能不能用」，M4~M5 是「好不好用」，M6~M7 是「强不强」。**
建议先把 M0~M3 做扎实，别跳。

**注意 M4 的位置**：它被提前了，因为"学了找不回来"是这个产品的核心痛点之一，而且它**不依赖 AI**（纯本地功能），风险低、见效快。

## 18. 预留：支付（做得好再接入）

> **本产品负责人决定：先预留接口，暂时不实现。** 和技术文档第 10.4/10.5 节配套。

### 18.1 为什么值得预留

因为**如果第一天不留口子，将来加付费要翻遍每一个功能入口**。
留口子的成本几乎为零：几个接口定义 + 三处 `if`。

### 18.2 一个必须先面对的矛盾

**你的用户已经自己付了 API 费用**（自带 Key、自配供应商）。
那你还收什么钱？这是付费设计里最核心的问题。

可能的答案（按我认为的合理度排序）：

| 卖什么 | 为什么说得通 | 依赖 |
|---|---|---|
| **云同步** | 自带 Key 解决不了「换设备板还在」 | 账号体系 |
| **托管模型服务** | 用户不想自己折腾 Key，你代付 API 费 + 收服务费 | 账号 + 支付 |
| **云端向量化 / 更强的资料检索** | 手机本地算不动 | 账号 |
| **买断制**（支持开发者） | 最简单，但和"本地免费也能用"的关系不大 | 无 |
| **捐赠** | 零门槛，但不构成商业模式 | 无 |

### 18.3 v1 只做三件事

1. 在代码里定义**权益点清单**（把将来可能收费的功能名先列出来）
2. 定义一个**查询有没有某权益**的接口，**v1 永远返回"有"**
3. 在少数几个相关功能入口调用它

**不做**：不写支付代码、不接任何支付 SDK、不加任何付费界面。

### 18.4 一个重要提醒

**把支付做好，主要不是技术问题，是合规和账务问题。** 资质、对账、退款、发票、税务 —— 这些才是成本所在。

而且渠道决定一切：

- **上 Google Play**：卖数字内容**必须用 Google Play Billing**（接微信/支付宝会被下架）
- **国内应用商店**：通常要**企业资质**，个人开发者门槛高
- **国内自接微信/支付宝**：个人很难拿到**商户资质**

⇒ **如果只是自己用或给朋友用，根本不需要支付。**

### 18.5 排期

支付**依赖账号体系**（权益要跟人走），而账号体系我们明确不做。
所以：**支付排在 M6（同步）之后，且要先有一个真实的付费理由。**
