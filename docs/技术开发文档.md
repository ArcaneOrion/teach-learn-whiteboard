## 1. 技术选型与理由

### 1.1 一句话结论

> **只用 TypeScript 一种语言。用 Web 技术画白板，用 pi-ai 接 AI，用 Capacitor 打包成安卓 App。**

### 1.2 每一层选什么

| 层 | 选什么 | 为什么 |
|---|---|---|
| 编程语言 | **TypeScript** | 全程唯一语言；pi-ai 就是它写的，直接能用；AI 编程助手对它最熟 |
| 构建工具 | **Vite** | 启动快、配置少，小白友好 |
| 界面框架 | **先不上 React，用原生 DOM** | 主界面就是一块画布，React 帮不上忙；少学一套概念。将来配置页复杂了随时能加，不影响架构 |
| 白板绘制 | **HTML Canvas 2D + Pointer Events** | 浏览器原生，能拿到压感、倾斜、掌托信息，零依赖 |
| AI 引擎 | **`@earendil-works/pi-ai`** | 46 家供应商 + 自配端点 + 流式 + 工具调用 + 图片输入，等于白捡 |
| 本地数据库 | **SQLite**（`@capacitor-community/sqlite`） | 手机本地、离线可用、支持全文检索 |
| 本地文件 | **Capacitor Filesystem**（App 私有目录） | **不需要任何存储权限** |
| 打包成 App | **Capacitor** | 把网页包成 APK，同时还能调安卓原生能力 |
| 网络请求 | **Capacitor 原生 HTTP** | 绕过浏览器跨域（CORS）限制，这是能否连上模型的关键 |
| 同步后端（M6） | **TypeScript**（Cloudflare Workers / 自托管） | 还是同一种语言 |

### 1.3 被否决的方案（以及为什么）

| 方案 | 否决理由 |
|---|---|
| **Kotlin 原生** | 用不了 pi-ai（它是 JS 库），得从零重写多供应商适配层；更要命的是 **AI 输出的是 HTML，Kotlin 得自己实现 MathML/HTML 渲染器 —— 不可行** |
| **Flutter** | Dart 生态没有 pi-ai 的对应物，同样要重写 |
| **React Native** | 语言对（TS），但手写低延迟仍要写原生模块，pi-ai 的 Node 依赖可能有坑，卡在中间不划算 |

### 1.4 为什么可以这么自信 —— 原型已跑通

DSH 的**教学平面**（`dsh-teaching-board`，1090 行，已发布 0.4.x）就是这套架构的一个可运行切片，它做到了：

- AI 把 HTML 投影成板书，可**反复写、局部擦、接着写**
- 用户在板上用笔画圈，**笔迹不会被 AI 的更新冲掉**
- AI 能把整块板（含用户笔迹）**拍成图片收回去看**
- 板面内容 = **会话日志折叠出来的**，客户端无私有状态

我们要做的，是把它从「DSH 插件」变成「独立的安卓 App」，并加上会话管理、本地检索与同步。
**这不是从零开始的赌注。**

## 3. 核心机制：事件日志（Event Log）

### 3.1 这是什么

**唯一真相（single source of truth）是一串「只追加、不修改」的事件。**
板面长什么样，是把这串事件**按顺序折叠**算出来的。

打个比方：**板面是电影画面，事件日志是胶片。** 画面可以随时重放出来，胶片本身永远不动。

### 3.2 为什么这么做（这是全文最重要的一个决定）

| 收益 | 说明 |
|---|---|
| **同步几乎白拿** | M6 要做的「联网同步」，本质就是**把这串日志推给服务器、再拉回来**。不需要处理「两边同时改同一块内容」的冲突，因为事件是不可变的、只增不改 |
| **撤销/重做免费** | 撤销 = 忽略最后一个事件重新折叠 |
| **完整学习记录免费** | 产品文档第 11 节的「记录」，是这套机制的副产品 |
| **可回放** | 能像放录像一样回放某块板是怎么长出来的 |
| **可搜索** | 每个事件都能投影出一段纯文本，塞进检索索引（第 9 节） |
| **可调试** | 出 bug 时，把日志导出来就能精确重现 |

### 3.3 事件类型

```ts
type Actor = 'user' | 'ai' | 'system';

type EventKind =
  // ── 板的生命周期 ──
  | 'board.create'      // 开一块板
  | 'board.rename'
  | 'board.archive'

  // ── AI 写板面（对应第 4 节的画布操作）──
  | 'ai.write'          // payload: { op:'append'|'set'|'remove', html?, region? }
  | 'ai.ask'            // payload: { choices: [{id,label}] }

  // ── 用户动作 ──
  | 'user.answer'       // payload: { choiceId }
  | 'user.say'          // payload: { text }  输入条里的字
  | 'user.mark'         // payload: { region, mark:'got-it'|'confused' }

  // ── 笔迹 ──
  | 'ink.stroke'        // payload: { color, size, erase, points:[[x,y,pressure,t]] }
  | 'ink.clear'

  // ── 视觉回流 ──
  | 'board.snapshot'    // payload: { attachmentId, caption? }

  // ── 反馈 ──
  | 'feedback'          // payload: { targetEventId, rating, comment? }

  // ── 🔲 预留：记忆（v1 不产生，但解析器认识它）──
  | 'memory.set'

  // ── 同步 ──
  | 'sync.marker';
```

```ts
interface BoardEvent {
  id: string;          // 全局唯一
  boardId: string;
  sessionId: string;   // ★ 会话归属（第 8 节）
  seq: number;         // 板内递增序号，决定折叠顺序
  actor: Actor;
  kind: EventKind;
  payload: unknown;    // JSON
  createdAt: number;   // 毫秒时间戳（UTC）
  deviceId: string;    // 哪台设备产生的（同步用）
  synced: 0 | 1;
}
```

**注意 `sessionId`**：每个事件同时归属「一块板」和「一次会话」，这是第 8 节的核心。

### 3.4 折叠（fold）

```ts
// 示意
function composeBoard(boardId: string, events: BoardEvent[]): BoardState {
  const state = { boardId, title: '', blocks: [] as Block[], choices: null, ink: [] as Stroke[] };
  for (const e of events.sort((a, b) => a.seq - b.seq)) {
    switch (e.kind) {
      case 'board.create': state.title = e.payload.title; break;
      case 'ai.write':     applyWrite(state, e.payload); break;   // append/set/remove
      case 'ai.ask':       state.choices = e.payload.choices; break;
      case 'user.answer':  state.choices = null; break;
      case 'ink.stroke':   state.ink.push(e.payload); break;
      case 'ink.clear':    state.ink = []; break;
      // ... memory.set 在这里留一个 case，v1 直接 break
    }
  }
  return state;
}
```

## 4. 核心接口：画布操作协议

**这是整个项目最重要的一个接口。** 它定义了「AI 允许对板做什么」。

### 4.1 设计原则

> **AI 的输出不是聊天文字，是一组画布操作。**

一旦想通这件事，整个产品就顺了 —— 因为操作是**有限的、可审计的、可撤销的**，而自由文本不是。

### 4.2 操作定义

```ts
type BoardOp =
  | { op: 'open';   title: string; html: string }        // 开一块新板（换主题）
  | { op: 'append'; html: string; region?: string }      // 在板尾追加一段
  | { op: 'set';    region: string; html: string }       // 替换某个区域
  | { op: 'remove'; region: string }                     // 擦掉某个区域
  | { op: 'ask';    choices: { id: string; label: string }[] };  // 出选项让用户点
```

**为什么必须有 `append` / `set` / `remove` 这三种，而不是「重发整块 HTML」？**
因为整块重发有三个代价（教学平面实测）：

1. **冲掉用户的笔迹**
2. **把滚动位置顶回顶部** —— 你正在看下面，它一下子把你拽回开头
3. **白烧 token** —— 一块 8KB 的板写十次 = 输出 80KB

「区域（region）」就是一个 HTML 元素上的标记：

```html
<section data-stage-region="讲解-第2步"> ... </section>
```

AI 想改「讲解-第2步」，就发一个 `{ op:'set', region:'讲解-第2步', html:'...' }`，只替换那一段。

### 4.3 怎么让 AI 调用这些操作 —— 用 pi-ai 的工具调用

pi-ai 支持**工具调用（tool calling / function calling）**，正好就是干这个的。
我们把画布操作**注册成工具**，模型就会以「调用工具」的形式来写板：

```ts
import { Type, type Tool } from '@earendil-works/pi-ai';

const canvasTools: Tool[] = [
  {
    name: 'board_write',
    description:
      '在白板上写入或修改内容。默认追加到板尾（append）。' +
      '要修改已有内容，用 set 并指定 region；要删除，用 remove。' +
      'html 必须是 self-contained 的 HTML 片段，公式用 MathML，不要引用外部资源。',
    parameters: Type.Object({
      op: Type.Union([Type.Literal('append'), Type.Literal('set'), Type.Literal('remove')]),
      region: Type.Optional(Type.String({ description: '区域名；op=set/remove 时必填' })),
      html: Type.Optional(Type.String({ description: 'HTML 片段；op=remove 时省略' })),
    }),
  },
  {
    name: 'board_open',
    description: '开一块新板。只有在明确开始一个全新主题时才用，否则会丢掉用户当前的笔迹。',
    parameters: Type.Object({ title: Type.String(), html: Type.String() }),
  },
  {
    name: 'ask_user',
    description: '给用户出选项，让他直接点选，而不是打字回答。适合「继续吗」「选哪种解法」这类。',
    parameters: Type.Object({
      choices: Type.Array(Type.Object({ id: Type.String(), label: Type.String() })),
    }),
  },
];
```

**注意**：这里**没有** `look_at_board` 工具了。视觉回流改由 UI 触发（用户截图 + 点发送），
模型只需要「被动地收到一张图」。理由见第 12 节。

**优雅之处**：AI 不需要「会写 HTML」，它只需要「会调用工具」。渲染、安全、撤销全部由我们控制。

### 4.4 安全：必须净化 AI 写的 HTML

AI 写的 HTML 会被插进页面，**必须过滤**（防 XSS）。做法：

- 白名单标签：`section div span p h1~h6 ul ol li table thead tbody tr td th strong em code pre br hr svg math ...`
- 白名单属性：`class style data-stage-region` + SVG/MathML 的必要属性
- **禁止**：`<script>` `<iframe>` `<object>` `on*` 事件属性、外部 `src`/`href`（只允许 `data:`）
- 用成熟库做（如 DOMPurify），不要自己写正则

> 教学平面是靠 `sandbox="allow-scripts"` 的 iframe 隔离的（无同源、无外网）。
> 我们也可以先照抄这个做法 —— **先隔离，后净化**，双保险。

## 5. 墨迹层（手指/笔迹绘制）

### 5.1 三层画布

```
┌─────────────────────────────────────┐
│ ③ 墨迹层  canvas（pointer-events 按需）│  ← 笔迹（最上）
├─────────────────────────────────────┤
│ ② 内容层  div（AI 写的 HTML）         │
├─────────────────────────────────────┤
│ ① 背景层  底色 / 网格                 │
└─────────────────────────────────────┘
```

**墨迹在最上层**，所以你能在 AI 写的东西上直接画，且 AI 更新内容层**不会碰你的笔迹**。

### 5.2 关键代码要点

```ts
// 示意：采集一笔
canvas.style.touchAction = 'none';   // 必须，否则浏览器会抢走手势

canvas.addEventListener('pointerdown', (e) => {
  if (e.pointerType === 'touch' && penActive) return;   // 掌托：笔在用时忽略手指
  if (e.pointerType === 'pen') penActive = true;
  canvas.setPointerCapture(e.pointerId);
  current = { color, size, erase, points: [[e.clientX, e.clientY, e.pressure, e.timeStamp]] };
});

canvas.addEventListener('pointermove', (e) => {
  if (!current) return;
  // ★ 关键：一帧内其实有多个采样点，getCoalescedEvents 能把它们都拿出来
  //   不取的话，快速书写会变成折线（锯齿感）
  for (const p of e.getCoalescedEvents?.() ?? [e]) {
    current.points.push([p.clientX, p.clientY, p.pressure, p.timeStamp]);
  }
  requestAnimationFrame(render);
});
```

### 5.3 必须处理的五件事

| 事项 | 做法 |
|---|---|
| **高分屏** | canvas 的实际像素 = CSS 尺寸 × `devicePixelRatio`，否则笔迹发虚 |
| **掌托误触** | `pointerType === 'pen'` 时忽略 `'touch'`；反之亦然 |
| **压感** | `e.pressure`（0~1）→ 线宽 = `baseSize * (0.4 + 0.6 * pressure)` |
| **撤销** | 笔画是数组，`pop()` 后重绘即可（**注意：canvas 没有「撤销」这个操作，必须全部重绘**） |
| **没有笔的设备** | 手机上没有笔时，手指写字也要能用；`pointerType==='touch'` 照样采集（只是没有压感） |

### 5.4 性能：两段式渲染

板子长了以后，每次移动都重绘几千条笔画会卡。做法：

- **已完成的笔画** → 画在一张离屏 canvas 上，只在笔画数量变化时重绘一次
- **正在画的那一笔** → 每帧清掉重画（只有一笔，很便宜）
- 每帧合成：`ctx.drawImage(committedCanvas); drawCurrentStroke();`

### 5.5 延迟：必须最早验证的风险

WebView 里的手写延迟比原生多 1~3 帧，写字够用但不如系统笔记应用。
**M0 就要用真笔真机体感验证。** 如果不可接受，逃生门是：

> 把 `ink/` 换成 Capacitor 插件里的**原生低延迟视图**（`androidx.ink` 或前台缓冲渲染）。
> 因为墨迹层和其余部分之间只有一个很窄的接口（对外只吐「一笔的点数组」），
> **换掉它不影响 AI、会话、检索、同步任何一行代码。** 这就是当初分层的意义。

## 6. AI 层：接入 pi-ai

### 6.1 基本结构

```ts
import { createModels, createProvider, type Context } from '@earendil-works/pi-ai';
import { openAICompletionsApi } from '@earendil-works/pi-ai/api/openai-completions.lazy';

// 1. 建模型集合（credentials 见第 7 节）
const models = createModels({ credentials });

// 2. 注册用户自配的供应商（任何 OpenAI 兼容端点都行）
const userProvider = createProvider({
  id: 'custom',
  name: '我的供应商',
  baseUrl: cfg.baseUrl,          // 例如 https://api.deepseek.com/v1
  auth: { apiKey: { name: 'API Key', resolve: async () => ({ auth: { apiKey: cfg.apiKey } }) } },
  models: cfg.models,
  api: openAICompletionsApi(),
});
models.setProvider(userProvider);

// 3. 取模型 / 装配上下文 / 带上工具去流式调用
const model = models.getModel('custom', cfg.modelId)!;
const stream = /* models.stream(model, context, { tools: canvasTools, ... }) */;
```

> ⚠️ 上面第 3 步的**确切写法要以 pi-ai README 的 Quick Start 与「Complete Event Reference」为准**，
> 真正写代码时我会对照文档写，不凭记忆。

### 6.2 上下文（Context）怎么装配

每次调用模型前，我们要把三样东西拼成 `Context`：

```
① 系统提示词
   └─ 「你在一块白板上教学，用 board_write 写板，不要用聊天口吻长篇大论…」

② 最近的事件（滚动的，不是全部）
   └─ 最近 N 条 ai.write / user.say / user.mark / ink.stroke(摘要)

③ 相关记忆   ← 🔲 预留，v1 永远传空数组
   └─ assembleContext(events, memories = [])
```

**②必须滚动截断**，否则板越长越贵、越慢，最后爆上下文窗口。这是所有长会话 AI 应用都会踩的坑，早点设计。

### 6.3 pi-ai 能力核查结果（实测）

| 能力 | 有没有 | 说明 |

| 自配端点 | ✅ `createProvider()` | 任何 OpenAI 兼容 API |
| 流式输出 | ✅ | |
| **工具调用** | ✅ | **画布操作靠它实现** |
| **图片输入（vision）** | ✅ | **视觉回流靠它实现** |

| **PDF/EPUB 解析** | ❌ **没有** | RAG 的文档解析要另外接 |

## 7. 供应商配置与 Key 安全

### 7.1 配置页要收什么

| 字段 | 说明 |
|---|---|
| 名称 | 用户自己起，如「DeepSeek 官方」 |
| Base URL | 如 `https://api.deepseek.com/v1` |
| API Key | 密码输入框，存本地 |
| 模型列表 | 可以手填，也可以用 pi-ai 的 `fetchModels` 自动拉 |

### 7.2 Key 存哪

- 通过 pi-ai 的 `CredentialStore` 接口注入我们自己的实现
- 后端是 SQLite（或 Capacitor Preferences）
- **绝不写进代码、绝不上传、日志里打码**

### 7.3 CORS —— 第一个必须验证的技术风险

网页 / WebView 直接调模型 API，常被浏览器**跨域策略（CORS）**挡住。

**解法**：Capacitor 自带原生 HTTP 能力，可以让请求走安卓原生网络栈，从而绕过 CORS。
**这是 M2 的第一件事，跑不通整个方案要重估。**

### 7.4 ⚠️ 明文 HTTP：本地模型服务会被安卓拦下

如果用户配的是**局域网里的服务**（比如 Ollama 跑在 `http://192.168.1.5:11434`），
安卓默认**禁止明文 HTTP 流量**，请求会直接失败，而且报错信息很难懂。

**解法**（二选一）：

| 做法 | 说明 |
|---|---|
| `<application android:usesCleartextTraffic="true">` | 一行搞定，但**对所有域名都放开**，不够精细 |
| **网络安全配置**（推荐） | 用 `network_security_config.xml` 只对**私有网段**放开明文 |

```xml
<!-- res/xml/network_security_config.xml：只对局域网放开明文，公网仍强制 HTTPS -->
<network-security-config>
  <domain-config cleartextTrafficPermitted="true">
    <domain includeSubdomains="true">192.168.0.0</domain>
    <!-- 实际要用 IP 段/主机名逐条列出；这里只是示意 -->
  </domain-config>
</network-security-config>
```

**这个坑必须在 M2 就处理掉**，否则「自主配置供应商」这个核心功能对本地模型用户直接不可用。

### 7.5 渠道策略：内置渠道 + 自配渠道

**已定：内置若干「免费但不稳定」的渠道，界面只暴露名称；同时保留自配渠道。**

两类渠道在引擎层是**同一件事** —— 都是 pi-ai 的 provider：

```ts
const models = createModels({ credentials });

// ① 内置渠道：端点与 key 打包在 App 里，界面只显示 name
for (const ch of BUILTIN_CHANNELS) {
  models.setProvider(createProvider({
    id: ch.id,
    name: ch.name,              // ← 用户只看到这个
    baseUrl: ch.baseUrl,
    auth: { apiKey: { name: ch.name, resolve: async () => ({ auth: { apiKey: ch.apiKey } }) } },
    models: ch.models,
    api: openAICompletionsApi(),
  }));
}

// ② 自配渠道：用户自己填 —— 同一个循环，只是数据来源不同
for (const p of await db.listProviders()) {
  models.setProvider(createProvider({ /* 用户填的 baseUrl / apiKey / models */ }));
}
```

界面上就是一个列表：

```ts
interface Channel {
  id: string;
  name: string;                 // ← 内置渠道对外暴露的全部信息
  kind: 'builtin' | 'user';
  unstable: boolean;            // 内置渠道恒为 true
}
```

**自配渠道的「预设」（预置 Base URL + 模型名 + 申请页链接）是可选项**，属于锦上添花，不是必须。

### 7.6 ⚠️ 内置渠道的界线与代价

#### 界线：公开渠道可以内置，你自己的付费 Key 不行

| 可以内置 | 不能内置 |
|---|---|
| **公开的免费渠道** —— 本来就人人可用，没有「秘密」可泄露 | **你自己的付费 API Key** |

后者的四个问题：APK 可解包（`strings` 一条命令就能提取）、泄露后无法恢复
（撤销 = 所有用户同时坏掉）、账单是你的、且多数厂商条款禁止分发 Key。

**区别的本质：前者泄露的是公开信息，后者泄露的是你的钱。**

#### 代价：必须用设计兜住

| 代价 | 兜法 |
|---|---|
| **渠道随时可能失效** | **「切换到自配渠道」必须永远显眼、永远可用** —— 否则渠道挂掉时，用户会以为是你的 App 坏了 |
| 渠道质量参差 | 界面如实标注「可能不稳定」，不承诺可用性 |
| **免费渠道可能记录内容** | **别把内置渠道包装成「隐私安全」** —— 「数据不出设备」这句承诺**只对自配渠道成立** |
| 出问题难排查 | 界面上始终显示「当前用哪个渠道」，出错时一眼看出 |

> 最后一条尤其重要：**产品最主要的那句隐私承诺，不能因为内置渠道而被稀释。**
> 诚实的做法是明确区分：
> **走内置渠道时，内容会经过第三方；走你自己的 Key 时不经过任何中间方。**

## 8. 会话与日期管理

### 8.1 概念模型

回顾产品文档第 8 节：**板 = 主题（长期），会话 = 一次坐下来学习（有始有终）**，两者正交。

技术上的落地只有两件事：

1. 加一张 `session` 表
2. **每个事件都带 `sessionId`**

```sql
CREATE TABLE session (
  id          TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL DEFAULT 'local',
  title       TEXT,                  -- 可选，用户命名或 AI 摘要
  started_at  INTEGER NOT NULL,      -- UTC 毫秒
  ended_at    INTEGER,               -- NULL = 还在进行中
  last_active INTEGER NOT NULL,      -- 最后一次有事件的时间
  device_id   TEXT NOT NULL
);
CREATE INDEX idx_session_started ON session(started_at);
```

### 8.2 会话边界判定：一个纯函数

```ts
const IDLE_MS = 15 * 60 * 1000;   // 空闲 15 分钟算结束

/** 决定"现在这次交互属于哪个会话" —— 纯函数，可测试，不依赖任何后台任务 */
function resolveSession(now: number, last: Session | null): { session: Session; isNew: boolean } {
  if (last && last.ended_at === null && now - last.last_active <= IDLE_MS) {
    return { session: { ...last, last_active: now }, isNew: false };  // 续上
  }
  if (last && last.ended_at === null) {
    // 上一个会话超时了 —— 补一个结束时间（补算，不需要后台任务）
    closeSession(last, last.last_active + IDLE_MS);
  }
  return { session: createSession(now), isNew: true };
}
```

**为什么不做「后台服务监控空闲」？**

| 后台服务的代价 | 补算法的好处 |
|---|---|
| 要有常驻服务，费电 | 零后台任务 |
| 安卓杀后台很凶，本来就不可靠 | 不依赖系统调度 |
| 可能还要通知/前台服务权限（违背第 15 节的零权限原则） | 零权限 |
| 难测试 | 一个纯函数，单测三行 |

**补算的含义**：不需要"实时"知道会话什么时候结束。下次打开 App 时算一下就行 —— 反正你也不可能在没打开 App 的时候产生学习记录。

### 8.3 时区：一个必须早定的坑

**存储统一用 UTC 毫秒时间戳，查询时才转本地时区。** 反过来（存本地时间）会在跨时区、夏令时、系统改时间时出各种诡异 bug。

```sql
-- 某天（本地时区）的所有会话
SELECT * FROM session
WHERE started_at >= :dayStart AND started_at < :dayEnd
ORDER BY started_at;
--  :dayStart / :dayEnd 由 JS 用本地时区算好后传入

-- 有记录的日子（日历打点）+ 那天学了多久
SELECT date(started_at / 1000, 'unixepoch', 'localtime') AS day,
       COUNT(*) AS sessions,
       SUM(COALESCE(ended_at, last_active) - started_at) / 60000 AS minutes
FROM session
GROUP BY day
ORDER BY day DESC;
```

⚠️ **注意**：`'localtime'` 用的是设备的时区设置。跨时区旅行时历史记录会重新分组 —— 这是可接受的，但要**知道**它会这样。

### 8.4 会话列表怎么查

```sql
-- 最近 50 次会话，带那次会话碰过的板（用于列表上显示"学了啥"）
SELECT s.*, GROUP_CONCAT(DISTINCT b.title) AS boards
FROM session s
LEFT JOIN event e ON e.session_id = s.id AND e.kind = 'board.create'
LEFT JOIN board b ON b.id = e.board_id
GROUP BY s.id
ORDER BY s.started_at DESC
LIMIT 50;
```

## 9. 本地存储与检索

### 9.1 存储布局

分两个位置，**都是 App 专属目录，都不需要任何权限**（原因见 §15.3）：

```
① App 内部私有目录 （Capacitor: Directory.Data）
   /data/data/<包名>/files
   └─ db/app.db                   SQLite 主库（小、要可靠、系统加密）

② App 专属外部目录 （Capacitor: Directory.External）
   /storage/emulated/0/Android/data/<包名>/files
   ├─ shots/2026/09/<id>.png      截图（大，按年月分目录）
   └─ docs/<docId>/…              导入的资料（M7）
```

**为什么分开放**：安卓官方建议「内部专属空间偏小，大文件放外部专属目录」。
数据库小且要可靠 → 内部；截图可能几百 MB → 外部专属。**两者都是零权限。**

### 9.2 为什么图片放文件、不放数据库

| 图片放文件（推荐） | 图片塞进 SQLite BLOB |
|---|---|
| 数据库保持小 → 备份/迁移/查询都快 | 数据库迅速膨胀 |
| 图片能被系统和其他工具直接打开 | 只能通过 App 看 |
| 出问题好排查 | 难排查 |
| ⚠️ 代价：DB 与文件可能不同步，需要清理任务兜底 | 事务一致性好 |

**我们选文件。** 用第 9.6 节的清理任务补上一致性。

### 9.3 附件表

```sql
CREATE TABLE attachment (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL DEFAULT 'local',
  session_id TEXT,                   -- 属于哪次会话
  board_id   TEXT,                   -- 属于哪块板
  event_id   TEXT,                   -- 由哪个事件产生
  kind       TEXT NOT NULL,          -- snapshot | imported | other
  rel_path   TEXT NOT NULL,          -- ★ 相对路径，不存绝对路径
  mime       TEXT,
  bytes      INTEGER,
  width      INTEGER,
  height     INTEGER,
  sha256     TEXT,                   -- 去重 & 完整性校验
  caption    TEXT,                   -- ★ AI 生成的一句话描述（见 9.5）
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_att_session ON attachment(session_id);
CREATE INDEX idx_att_board   ON attachment(board_id);
CREATE INDEX idx_att_sha     ON attachment(sha256);
```

**为什么存相对路径**：安卓上 App 的私有目录绝对路径可能随安装/系统版本变化（尤其 `Android/data/...`）。
存绝对路径会导致换设备或重装后全部失效。**存相对路径，用时再拼。**

### 9.4 统一检索索引

搜的东西来自很多张表（事件、附件、板、会话），统一塞进一张"检索文档"表：

```sql
CREATE TABLE search_doc (
  id         INTEGER PRIMARY KEY,
  ref_kind   TEXT NOT NULL,          -- event | attachment | board | session
  ref_id     TEXT NOT NULL,
  session_id TEXT,
  board_id   TEXT,
  title      TEXT,                   -- 板名 / 会话名 / 文件名
  body       TEXT NOT NULL,          -- ★ 纯文本正文
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_sd_session ON search_doc(session_id);
CREATE INDEX idx_sd_board   ON search_doc(board_id);
CREATE INDEX idx_sd_created ON search_doc(created_at);
```

**入库规则**：

| 来源 | `body` 怎么来 |
|---|---|
| `ai.write` | **HTML 剥掉标签取纯文本**（不是存 HTML！否则搜"section"全是结果） |
| `user.say` | 原文 |
| `board.create` / `session` | 标题 |
| `attachment` (snapshot) | **AI 生成的 caption**（见 9.5） |

剥标签：最简单是一个 `DOMParser` 取 `textContent`；注意要在**净化之后**做。

### 9.5 让截图"可被文字搜索"：caption 生成

**问题**：截图是图片，关键词搜不到。

**做法**：截图入库时，**后台单独发一次轻量的视觉调用**，让模型用一句话描述这张图，存进 `attachment.caption`，同时写进 `search_doc.body`。

**为什么成本几乎为零**：那一刻图片本来就要发给模型看（视觉回流），多问一句话的代价极小。
而且这次调用可以**用最便宜的模型**（描述图片是简单任务）。

**为什么要在后台单独做、不塞进主循环**：

| 塞进主循环 | 后台单独调用（推荐） |
|---|---|
| 要在系统提示词里要求模型"先描述再干活" | 主循环干净，提示词不用为检索服务 |
| 模型可能忘了写，或写进板面污染板书 | 失败也不影响主流程 |
| 主循环的 token 变贵 | 可以用便宜模型 |

```ts
// 示意
async function captionSnapshot(imageRef: string): Promise<string> {
  const ctx: Context = {
    messages: [{
      role: 'user',
      content: [
        { type: 'text', text: '用一句中文描述这张白板截图：用户写了什么、圈了哪里、在问什么。只输出这一句话。' },
        { type: 'image', /* ...图片输入... */ },
      ],
      timestamp: Date.now(),
    }],
  };
  return (await models.complete(cheapVisionModel, ctx, { apiKey })).text.trim();
}
```

> ⚠️ 图片内容对象的确切结构以 pi-ai README 的「Image Input」章节为准。

### 9.6 检索怎么实现（分阶段）

| 阶段 | 做法 | 适用 |
|---|---|---|
| **起步（推荐）** | `WHERE body LIKE '%' \|\| :q \|\| '%'` | **2 万条以内完全够用**，中文完美，零依赖零维护 |
| 进阶 | FTS5 全文索引 | 数据量真的很大时 |

**起步别上 FTS5**，原因见下 —— 中文在 SQLite 全文检索里有个很多人踩过的坑。

#### ⚠️ FTS5 中文的三个坑（重要）

| 坑 | 说明 |
|---|---|
| **默认分词器不切中文** | `unicode61`（默认）会把一整句中文当成**一个词**，所以搜"方程"匹配不到"一元二次方程" |
| **trigram 分词器要求关键词 ≥3 字** | `tokenize='trigram'` 确实能搜中文子串，但 **「函数」「方程」「判别式」这种两字词直接搜不到** —— 而中文里两字词极多 |
| ICU 分词器不可用 | SQLite 要带 ICU 编译才支持真正的中文分词，安卓上不一定有 |

**可行的绕法**（数据量大时再用）：入库前把中文**逐字加空格**，查询时同样处理并用**短语查询**。

```
入库：一元二次方程  →  一 元 二 次 方 程
查询：二次          →  "二 次"        （FTS5 短语查询，匹配相邻两个 token）
```

这样两字词也能搜到。代价是索引变大、要维护预处理逻辑。

**结论：M4 用 `LIKE` 就好。** 等真的上万条、明显变慢，再按上面这套上 FTS5。

### 9.7 数据量与清理

截图是大头。要有：

```sql
-- 存储占用排行（按会话）
SELECT s.id, s.started_at,
       COUNT(a.id) AS files, SUM(a.bytes) AS bytes
FROM session s LEFT JOIN attachment a ON a.session_id = s.id
GROUP BY s.id ORDER BY bytes DESC LIMIT 20;
```

| 任务 | 做法 |
|---|---|
| **孤儿文件清理** | 扫 `shots/` 目录，找出 `attachment` 表里没有的文件 → 删 |
| **悬空记录清理** | 扫 `attachment` 表，找出磁盘上不存在的文件 → 删记录 |
| **只删图不删笔记** | `DELETE FROM attachment WHERE session_id=?` + 删文件；`search_doc` 里的 caption 保留 |
| **压缩** | 定期 `VACUUM`（SQLite 删数据不会自动缩小文件） |
| **导出** | 全部数据 + 图片打包成一个 zip，用户自己保存 |

⚠️ **孤儿清理和导出都必须在 M4 就有**，否则用户装了两周发现占了 2GB，就只能卸载重装。

## 10. 预留接口（记忆 / 支付，v1 不实现）

**产品决定：记忆先不设计、支付先不实现，两者都只留接口。** 本节只讲**留什么钩子**，不讲怎么实现。

### 10.1 记忆：三个必须留的钩子

| 钩子 | 怎么留 | 不留的后果 |
|---|---|---|
| ① **事件类型** | `EventKind` 里保留 `'memory.set'`；`composeBoard` 里留一个空 `case` | 以后加记忆要改事件类型定义，可能要迁移历史数据 |
| ② **装配函数签名** | `assembleContext(events, memories = [])`，v1 永远传 `[]` | 以后要给所有调用点加参数 |
| ③ **数据表** | DDL 写在下面 §11.6，**标注"预留，v1 不建表"** | 无需重建库 |

### 10.2 记忆：明确不做的事

- ❌ 不写记忆提取逻辑
- ❌ 不做记忆检索
- ❌ 不做记忆查看页（产品文档第 7 节的"记忆查看"标为 🔲 预留）
- ❌ 上下文装配的第 ③ 块永远传空

### 10.3 为什么要写这一节

因为**"不做"也需要留痕**。三个月后你回来看，会知道这里是有意留空的，
而不是"当时忘了做" —— 这两者的处理方式完全不同。

### 10.4 支付：留什么钩子

> 产品决定：**先预留接口，如果产品做得好再接入支付。**

**核心思路：把「有没有某项权益」抽象成一次查询。业务代码只问这个查询，不关心钱是怎么收的。**

```ts
// 权益点：从第一天就定义好。v1 全部返回 true（因为没有付费墙）
type FeatureKey =
  | 'cloud.sync'        // 云同步
  | 'cloud.embedding'   // 云端向量化（RAG）
  | 'hosted.model';     // 托管模型服务（用户不用自己配 Key）

interface EntitlementProvider {
  has(key: FeatureKey): Promise<boolean>;              // 查询权益
  purchase(key: FeatureKey): Promise<PurchaseResult>;  // v1: 抛 NotImplemented
  restore(): Promise<void>;                            // v1: 空实现（换设备恢复购买）
  onChange(cb: () => void): () => void;                // 权益变化通知（到期等）
}
```

v1 的实现（`LocalEntitlements`）只有十几行：

```ts
/** v1：没有付费墙，一切都是 true。但它让业务代码的形状先对。 */
class LocalEntitlements implements EntitlementProvider {
  async has(): Promise<boolean> { return true; }
  async purchase(): Promise<PurchaseResult> { throw new Error('NOT_IMPLEMENTED'); }
  async restore(): Promise<void> { /* 空 */ }
  onChange(): () => void { return () => {}; }
}
```

**关键纪律：只在「将来可能收费」的功能入口调用 `has()`，不要到处撒。**
v1 大概只有 3 个地方：云同步、云端向量化、托管模型。
**加这三处 `if` 的成本几乎为零，但不加的话，将来接支付要翻遍每一个功能入口。**

> 💡 **`hosted.model` 从第一天就有真实使用者。**
> 它是「试用通道」的接口（§7.6）：内置你自己的代理地址，用户零配置可试用 N 次。
> 所以这个预留点不是"以后可能用得上"，而是**产品定位里已经规划好的东西**。

**⚠️ 一个语义澄清（别写错）**：

| `has()` 回答的是 | **不**回答 |
|---|---|
| 用户**有没有权**用这个功能 | 这个功能**做没做** |

v1 没有付费墙，所以 `has()` 永远返回 `true`。
但「试用通道（hosted.model）」本身**在 v1 就没实现** —— 它的入口根本不该显示。
「功能是否已经存在」由功能自身决定（入口有没有做），**不要塞进权益判断里**。

### 10.5 支付：明确不做的事 + 三个前提

❌ v1 不写任何支付代码、不接任何支付 SDK、不加任何付费界面。

**三个前提，缺一个都不该动支付：**

| 前提 | 为什么 | 现状 |
|---|---|---|
| **① 账号体系** | 权益必须跟人走，否则换设备/重装就丢 | 账号体系 **v1 明确不做** → **支付实际排在 M6 之后** |
| **② 想清楚卖什么** | 见下方的"真实矛盾" | ❓ 待产品负责人回答 |
| **③ 确定分发渠道** | 渠道决定支付方式，差别极大 | ❓ 待回答 |

**真实矛盾**：用户**已经自己付了 API 费用**（自带 Key、自配供应商）。那你收什么钱？
这个问题不想清楚，支付接口留了也没用。

**渠道决定支付方案：**

| 渠道 | 支付方式 | 合规成本 |
|---|---|---|
| 只给自己/朋友装 APK | 不需要支付，或转账/捐赠 | 零 |
| **Google Play** | **必须用 Google Play Billing** | Play 政策：卖数字内容/功能必须走 Billing；接微信/支付宝会被下架 |
| 国内安卓商店（华为/小米/OPPO/vivo） | 各商店自有支付 SDK | 通常需**企业资质**，个人开发者门槛高 |
| 国内独立分发 + 微信/支付宝 | 微信支付 / 支付宝 | **个人很难拿到商户资质**，需营业执照 |

> ⚠️ **本节最重要的一句话**：把支付做好，**主要是合规和账务问题，不是技术问题**。
> 技术上「一个接口 + 一个 Provider」就够了；真正的成本在资质、对账、退款、发票、税务。
> **如果只是自己用或给朋友用，根本不需要支付。**

**本地优先带来的额外要求**：权益必须**离线可用**（缓存权益 + 定期校验 + 宽限期），
否则「断网就打不开自己买过的功能」，体验极差。

## 11. 数据模型（SQLite）

> 所有表**从第一天就带 `user_id` 字段**，默认填 `'local'`。现在多花一分钟，以后接账号体系省一周。
>
> **M1 就把所有表建全**（包括 v1 暂时不用的），因为改表结构比建表贵得多。

### 11.0 ⚠️ 一处实现偏差：v1 落盘用的是 IndexedDB，不是 SQLite

**已实施**（M1）：持久化用的是 **IndexedDB**，而不是下面写的 SQLite。

| | IndexedDB | SQLite（Capacitor 插件） |
|---|---|---|
| 依赖 | **零** | 网页端要引 WASM + 一个 web component |
| 开发环境 | 电脑浏览器和安卓 WebView **同一套代码** | 网页端要另搭一套 |
| 事件日志需要的能力 | 追加 + 按板顺序读 —— **正好够** | 也能做，但用不上 SQL |
| 全文检索 | JS 扫描（§9.6 已认可 2 万条内够用） | FTS5 更快，但中文有坑（§9.6） |

**为什么不影响架构**：所有业务代码只依赖 `src/store/types.ts` 的 `Store` 接口。
将来真要上 SQLite，加一个实现即可，业务代码一行不改。
（测试是**两个实现跑同一套契约测试**，避免"内存版通过、真机版出问题"。）

**什么时候可能需要换**：

- 数据量到了 JS 扫描明显变慢（§9.6 判断是 2 万条以上）
- 需要 SQLite 的强事务保证
- **安卓 WebView 的存储被系统清理**（见风险登记 —— 这是要留意的点）

> **所以下面的建表语句仍然保留**：它描述的是「数据长什么样」，而不是「必须用 SQL 存」。
> 字段和关系本身就是设计 —— 换存储不该改设计。

## 12. 视觉回流（截图 + 输入条）

### 12.1 原理

**AI 看不见画布上的像素。** 唯一的办法是：**把板面拍成图片，作为「图片输入」发给模型**。pi-ai 支持图片输入。

### 12.2 交互流程（按你的设计）

```
用户圈了一处 → 点「📷 截图」→ 弹出输入条 → 写字（可空）→ 点「完成/发送」
                                                          ↓
                                     截图 + 输入条文字 一起作为一条用户消息
                                                          ↓
                                        AI 同时看到「板面长什么样」和「你想说什么」
```

**一次「让 AI 看」传达三件事**：板面现状（图）、你圈了哪（图里）、你想说什么（文字）。

### 12.3 事件与数据的落法

一次发送产生**一个事件**（截图和文字是同一条消息的两部分，不该拆开）：

```ts
// kind: 'board.snapshot'
payload: {
  attachmentId: string,     // 指向 attachment 表里的截图
  caption: string | null,   // 后台生成的图说（9.5），稍后回填
  text: string | null,      // 输入条里的文字（可以为空）
}
```

> 为什么 `text` 放在 `board.snapshot` 里，而不是单独发一条 `user.say`？
> 因为它们是**同一次发送**。拆开会让折叠逻辑、回放、检索都变复杂。
> 而**用户单独打字发送**（没截图）仍然是 `user.say`。

### 12.4 实现要点

| 项 | 做法 |
|---|---|
| **截图范围** | 默认**当前视口**（所见即所得），不是整页长图 |
| **必须含笔迹层** | 否则 AI 看不见你圈的 |
| **先落盘再发送** | 截图先存文件 + 写 `attachment` 行，再拿 `attachmentId` 去发 |
| **体积控制** | 单图超过约 1.2MB 就退化 JPEG 或等比缩小（模型对单图有预算） |
| **触发方式** | 默认**手动**（用户点发送），可选开启自动 |
| **caption 异步** | 图说在后台生成，不阻塞主流程；失败就不填，不影响使用 |

### 12.5 一个共享的能力

这条能力和 RAG 的**扫描版书籍**是同一个：都是「把画面变成模型能看的东西」。
所以 M3 做完，M7 的扫描书部分就顺带有了。

## 13. 同步设计（M6）

### 13.1 核心洞见

> **有了事件日志，同步 = 把日志推上去、拉下来。**

因为事件**不可变**，不存在「两边同时改同一个东西」的冲突。
唯一要处理的是**顺序**：用 `(createdAt, deviceId)` 做全局排序，保证所有设备折叠出同样的板面。

### 13.2 协议

```
push：把本地 synced=0 的事件批量上传 → 成功后置 synced=1
pull：带上本地已有的最大 (createdAt, deviceId) → 服务器返回之后的事件
```

冲突策略：**同一个 `seq` 上两端各写了一条？** 极罕见（要同时离线改同一块板）。用 `deviceId` 字典序定胜负即可（LWW，Last-Write-Wins）。

### 13.3 分阶段

| 阶段 | 做法 | 目的 |
|---|---|---|
| **先** | **导出/导入一个 zip 文件**（含数据 + 截图） | 零后端，先把数据模型和折叠逻辑验证对 |
| M6 | Cloudflare Workers + D1（或自托管） | 真同步 |

**别跳过第一步。** 一个文件导入导出，能验证掉 80% 的数据模型问题，而且不需要写任何后端。
**而且它顺便就是产品文档第 9.7 节要的「导出后清空」功能。**

### 13.4 边界（想清楚再动手）

- 笔迹数据量不小（一条笔画几十个点）。要不要压缩？要不要只同步「已结算」的笔画？
- **截图同步吗？** 几百张图可能是几百 MB。建议：默认**不同步截图**，可选。
- 断网时怎么办？（本地继续用，联网后补推）

## 14. RAG 设计（M7，先不急）

**定位：让 AI 去检索用户上传的文件，不是全量喂进上下文。**

| 步骤 | 做法 |
|---|---|
| 导入 | Web 层用 `pdf.js` 抽 PDF 文本；TXT/MD 直接读；EPUB 用解析库 |

## 15. 权限（Android）

### 15.1 目标：零弹窗

**这个 App 的目标是：安装后打开，系统不弹任何权限请求框。**

| 权限 | 声明 | 类型 | 会弹框吗 |
|---|---|---|---|
| `android.permission.INTERNET` | ✅ 需要 | 普通权限 | ❌ 不弹（装机自动授予） |
| `android.permission.ACCESS_NETWORK_STATE` | ✅ 需要 | 普通权限 | ❌ 不弹 |
| `READ_EXTERNAL_STORAGE` / `READ_MEDIA_*` | ❌ **不要** | 危险权限 | — |
| `CAMERA` | ❌ 不要（v1） | 危险权限 | — |
| `RECORD_AUDIO` | ❌ 不要 | 危险权限 | — |
| `POST_NOTIFICATIONS` | ❌ 不要（v1） | 危险权限 | — |
| 位置 / 通讯录 | ❌ **绝对不要** | 危险权限 | — |

### 15.2 AndroidManifest.xml 最终应该只有这两条

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <uses-permission android:name="android.permission.INTERNET" />
    <uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
    <!-- 其它一个都不要 -->
    <application ...>
</manifest>
```

⚠️ **Capacitor 生成的安卓工程默认可能带别的权限**，**第一次生成后必须逐条审计并删掉**。
这是一条明确的验收项。

### 15.3 存储权限：为什么不需要（以及什么时候才需要）

**安卓官方文档原话**（developer.android.com，Access app-specific files）：

> "Your app doesn't require any system permissions to read and write to files in these directories."

这个"这些目录"指 **App 专属目录**，分两种：

| | 内部专属 | 外部专属 |
|---|---|---|
| 安卓 API | `context.filesDir` | `context.getExternalFilesDir()` |
| 实际路径 | `/data/data/<包名>/files` | `/storage/emulated/0/Android/data/<包名>/files` |
| **要权限吗** | ❌ **任何安卓版本都不要** | ❌ **安卓 4.4 (API 19) 起就不要** |
| 安卓 10+ | 系统加密 | 作用域存储 |
| 别的 App 能看到吗 | 不能 | 不能（安卓 10+） |
| 空间 | 偏小 | 大 |
| 卸载 App 后 | **删** | **删** |

**分工**（对应 §9.1）：数据库 → 内部专属；截图和资料 → 外部专属。**两者都零权限。**

#### ⚠️ 坑一：`Directory.Documents` 在安卓和 iOS 上不是一回事

Capacitor 的目录枚举里有两个特别容易踩雷：

| Capacitor 目录 | iOS 上 | **Android 上** | 要权限吗 |
|---|---|---|---|
| `Directory.Data` | App 文档目录 | App **内部私有**目录 | ❌ **不要** |
| `Directory.External` | App 文档目录 | App **专属外部**目录 | ❌ **不要** |
| `Directory.Documents` | App 文档目录 | **公共 Documents 文件夹**（别的 App 能看！） | ⚠️ **安卓 10 及以下要 `READ/WRITE_EXTERNAL_STORAGE`** |
| `Directory.ExternalStorage` | App 文档目录 | 公共外部存储根目录 | ⚠️ 要权限，且**安卓 11+ 已不可用** |

**同名不同义**：在 iOS 上 `Directory.Documents` 是「App 自己的文档目录」，
在 Android 上却是**公共** Documents 文件夹。**照着 iOS 的直觉去用它，就会在安卓上引入存储权限。**

Capacitor 专门为此提供 `checkPermissions()` / `requestPermissions()`，文档写明：

> "Required on Android, **only when using `Directory.Documents` or `Directory.ExternalStorage`**."

—— 换句话说：**不用这两个，权限就永远是 0。**

#### ⚠️ 坑二：卸载 App 会删掉全部数据

App 专属目录（内部和外部都算）**卸载即删**，这是安卓的设计。
官方文档也提醒：不要把「用户期望独立于 App 长期存在」的东西放这里。

对本产品这是个**真实风险**：截图、学习记录、会话历史都属于那类东西。

| 应对 | 说明 |
|---|---|
| **导出备份是必需功能，不是锦上添花** | M5 的导出优先级要提到「没有它就不能用」（见 §19 风险） |
| 导出去哪 | 用 SAF 让用户自己选位置（公共目录 / 云盘 App），**依然不需要权限** |
| 可选：安卓自动备份 | `android:allowBackup` 默认开，但额度有限（约 25MB），装不下截图 |

#### 那什么时候才真的需要存储权限？

| 场景 | 要权限吗 |
|---|---|
| 读取**别的 App** 创建的图片 / 视频 | ⚠️ 要 `READ_MEDIA_IMAGES` 等（安卓 13+） |
| 遍历整个外部存储 | ⚠️ 要 `MANAGE_EXTERNAL_STORAGE`，Google Play 管控极严 |
| 把自己的图放进系统相册、让别的 App 看到 | ❌ **不用**（安卓 10+ 用 MediaStore 插自己的文件，零权限） |
| 用户自己选文件导入 / 导出 | ❌ **不用**（SAF 给临时授权） |
| **我们的全部场景** | ❌ **不用** |

> **一句话总结：只要数据待在自己的沙盒里，就永远不需要存储权限。**

### 15.4 安卓端还要处理的非权限事项

| 事项 | 说明 |
|---|---|
| **明文 HTTP** | 局域网模型服务需要网络安全配置，见 §7.4 |
| **手写笔特性** | `<uses-feature android:name="android.hardware.touchscreen" android:required="false" />`，别把没触屏的设备排除了 |
| **屏幕方向** | 白板在横竖屏都要能用；注意旋屏时 canvas 重算尺寸 + 笔迹坐标要跟着变换 |
| **返回键** | 安卓返回键要能在「搜索页/会话页」返回白板，别直接退出 App |
| **后台** | 切到后台时把当前笔迹和事件**立即落盘**（安卓可能随时杀进程） |

### 15.5 将来要加权限时的规矩

1. **用到时才申请**（不要启动就申请一堆）
2. **申请前说明为什么**（一句话，说人话）
3. **拒绝了也要能用**（拒绝相机 → 还能用文件选择器导资料）
4. **同步更新本文档和产品文档第 10 节**

## 17. 跑起来（M0 环境搭建）

> 具体命令等我搭的时候会一条条给你，并解释每条在干什么。

```bash
# 大方向（示意）
pnpm create vite@latest . --template vanilla-ts   # 建 TypeScript 网页工程
pnpm add @earendil-works/pi-ai                    # AI 引擎
pnpm add @capacitor/core @capacitor/cli           # 打包成 App
pnpm add @capacitor-community/sqlite              # 本地数据库
pnpm add @capacitor/filesystem                    # 本地文件（截图）—— 零权限
pnpm dev                                          # 电脑浏览器里跑起来 ← 开发主力
npx cap add android                               # 生成安卓工程
npx cap run android                               # 装到手机上
```

**开发主力是电脑浏览器**，只在需要验证手写手感、CORS、权限、原生能力时才上真机。
这对小白是巨大的效率优势。

**第一次 `cap add android` 之后立刻做两件事**：
1. 审计 `android/app/src/main/AndroidManifest.xml`，删掉多余权限（§15.2）
2. 确认没有多余弹窗

## 18. 里程碑与验证清单

每个里程碑都配一个**必须验证的假设**——假设不成立就要停下来重估，而不是硬着头皮往下做。

> ⚠️ **设备现状（已确认）**：当前测试设备是**安卓手机，没有手写笔**。
>
> - M0 / M1 / M2 **不依赖笔，可以正常推进** —— 工程链路、事件折叠、AI 调用都能验
> - 但 **「手写延迟」这个头号风险无法验收**：手指书写的延迟特性与笔完全不同，
>   用手指能画 ≠ 用笔能写
> - **待办**：借一台安卓平板，或买一支支持安卓手机的主动式笔（部分三星/小米机型支持），补做这项验收
> - 在补上之前，此风险状态为 **「已识别、未验证」** —— 不代表它不存在，只代表我们还不知道答案

| 里程碑 | 交付 | **必须验证的假设** |
|---|---|---|
| **M0** | 白板能画线，能在安卓**手机**上跑起来 | ① 工程链路通（真机能画线）② 高分屏不发虚 ③ **manifest 里只有 2 个权限、不弹框** ④ 返回键不退出 App、旋屏不丢笔迹<br>⏸ **手写延迟：设备无笔，未验收**（见上方待办） |
| **M1** | 事件日志 + 板面折叠 + **会话表（数据模型一次到位）** + 假 AI 写板 | ① 折叠逻辑正确 ② SQLite 真机能读写 ③ **时区分组正确**（把系统时区改一下试试）④ 旋屏不丢笔迹 |
| **M2** | 真 AI：配 Key + 流式 + 工具调用写板 | ① **CORS 能绕过**（最关键）② **局域网明文 HTTP 能通**（§7.4）③ 工具调用能被正确解析执行 |
| **M3** | 视觉回流：截图 + 输入条 → 发送 | ① 截图含笔迹层 ② 图片体积可控 ③ 模型确实"看懂了"圈画 ④ caption 生成不阻塞主流程 |
| **M4** | 会话与日期管理 + 本地检索 + 存储管理 | ① 日期分组/日历正确 ② **搜关键词能搜到截图**（靠 caption）③ 2 万条内 `LIKE` 不卡 ④ 孤儿清理正确 |

| **M6** | 同步 | ① 两台设备折叠结果一致 ② 断网恢复不出错 ③ 截图默认不同步的边界清楚 |

## 19. 风险登记

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| **手写延迟不可接受** | 中 | 高 | M0 就体感验证；逃生门 = 换原生墨迹视图（接口已隔离） |
| **CORS 挡死** | 中 | 高 | M2 第一件事验证；Capacitor 原生 HTTP；极端情况自建代理 |
| **局域网明文 HTTP 被拦** | **高** | 中 | 网络安全配置，§7.4。不处理的话"自配供应商"对本地模型用户直接不可用 |
| **存储无限增长** | **高** | 中 | M4 必须做占用查看 + 孤儿清理 + 只删图不删笔记 |
| **DB 与文件不同步** | 中 | 中 | 双向清理任务（孤儿文件 / 悬空记录），§9.7 |
| **时区处理错导致日期分组乱** | 中 | 低 | 统一 UTC 存、查询转本地；M1 就验证 |
| **pi-ai 浏览器打包踩坑** | 中低 | 中 | 只注册用到的 provider；必要时换 Vite 配置；最坏情况自己写一层 30 行的 OpenAI 兼容调用 |
| **AI 写的 HTML 出安全问题** | 低 | 高 | 沙箱 iframe + DOMPurify 双保险 |
| **上下文越用越贵/越慢** | 高 | 中 | 事件滚动截断 + 记忆聚合（6.2） |
| **功能太多做不完** | **高** | **高** | 产品文档第 15 节的「明确不做」清单；先做扎实 M0~M3 |
| **卸载 App 会删掉全部数据** | 中 | **高** | App 专属目录卸载即删（§15.3 坑二）。**导出备份必须在 M5 就做**，且要显眼提示用户 |
| **WebView 存储可能被系统清理** | 中 | **高** | v1 把事件日志存在 IndexedDB（WebView 的数据目录）。安卓在存储紧张时可能清理；用户"清除数据"也会清掉。**对策：导出备份（M5）+ M4 起评估换原生 SQLite** |

## 20. 给你的学习路径（不按这个顺序会很难受）

| 顺序 | 学什么 | 什么时候学 |
|---|---|---|
| 1 | **能跑起来**：装环境、敲命令、看到白板出现 | M0 |
| 2 | **数据长什么样**：JSON 是什么、事件是什么、折叠是什么 | M1 |
| 3 | **代码怎么组织**：什么是模块、什么是接口、为什么分层 | M1~M2 |
| 4 | **TypeScript 类型**：为什么写 `: string`、类型能帮你防什么错 | M2 |
| 5 | **异步**：为什么有 `await`、为什么要等 | M2 |
| 6 | **SQL**：只学 4 个动词：建表 / 插入 / 查询 / 更新 | M4 |

**不要从语法书第一页开始看。** 每一块都在你**已经看到它有用**之后再学，会快十倍。
